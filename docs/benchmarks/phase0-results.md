# Phase 0 Benchmark Results

> Generated by build/scripts/phase0-benchmarks.ps1. Each run appends a timestamped section.

## Summary — decisions this file settles (as of 2026-07-06, hardware: GTX 1660 6GB)

**A1 — context cap: 8k fits, barely.** Idle free VRAM ran 3.5–4.1GB across three separate
measurements (one real 10-minute window: 3539MB), well below the plan's assumed 5.2–5.5GB usable —
this desktop carries more baseline GPU load than the plan estimated (LM Studio and Visual Studio
were both open during testing, which is realistic day-to-day load, not an inflated test condition).
At ctx-size 8192 without forcing full GPU offload, peak VRAM was 5529–5557MB against 6144MB total —
a 587–615MB margin, which clears the plan's ≥300MB bar but with less room than assumed. Forcing
`-ngl 999` (full GPU offload) reliably crashed llama-server with a Vulkan `ErrorDeviceLost` at ctx
8192 — this card cannot fit all layers on GPU at that context length; the working configuration
lets llama-server auto-select how many layers to offload. **Verdict: keep the 8k cap, do not force
full offload — auto-fit layers.** ctx 10240 loaded without a VRAM jump (5557 vs 5529MB), because the
auto-fit config already keeps a chunk of the model on CPU; the "spill" the plan expects manifests as
CPU-bound layers, not a VRAM cliff.

**A2 — throughput baseline is CPU-bottlenecked.** No-draft generation held at 6.1–7.8 tok/s across
three runs regardless of prompt length; prompt processing ran 38–45 tok/s. These are low for a
7B on a discrete GPU — consistent with partial (not full) GPU offload, which A1 shows is required
on this hardware to avoid crashing. Trivial/complex single-file targets in the plan (<10s / <60s)
are not met by the no-draft path at these generation speeds for anything beyond a very short reply.

**A3 — speculative decode clearly pays off. Ship the 0.5B draft.** With `--model-draft` +
`--spec-draft-n-max 8` (note: the plan's `--draft-max` flag has been renamed in current llama.cpp
builds), generation on the 5 real C# tasks ran 18.3–19.1 tok/s vs. 6.1–7.8 tok/s baseline — roughly
**2.4–2.9x speedup**, well past the plan's ≥1.3x pass bar. Long synthetic fill prompts (8000 tok)
saw a smaller but still positive gain (12–12.5 tok/s vs ~6.1–7.1 tok/s baseline, ~1.7–2x). Draft
acceptance rate (proposed/accepted token counts) could not be captured — this llama-server build's
`/completion` response doesn't expose `draft_n`/`draft_n_accepted` in `timings`; the speedup number
itself is the decision-relevant metric and it clears the bar regardless.

**A4 — router latency fails the "every request" bar; needs a pre-filter.** Qwen2.5-1.5B-Instruct on
CPU with JSON-schema-constrained decoding ran p50 ≈ 3.3–3.4s, p95 ≈ 4.5–4.7s against the plan's
p95 < 1.5s pass threshold — roughly 3x over. Schema validity was 100% (20/20) both runs, confirming
constrained decoding is reliable. Informal intent-match against hand-labeled expectations was 16/20
(80%) both runs — not the real A5 golden-set metric, but the two visible failure patterns (`meta`
prompts read as `question`; one `explanation` read as `code_generation`) are worth carrying into
golden-set design. **Verdict: do not run the router on every request — add the cheap heuristic
pre-filter (length, code fences, keywords) the plan proposes, router only on inconclusive cases.**

**Not covered: A5** (classification accuracy) — requires the Part B golden set (`tests/golden/`),
which doesn't exist yet.

## CUDA backend rerun (2026-07-06, llama.cpp b9878, CUDA 12.4 and 13.3 builds)

Re-ran A1/A2/A4 against llama-server's CUDA build (driver reports CUDA 13.3; both the 12.4 and
13.3 release builds were tested) instead of the winget-installed Vulkan build, to see whether CUDA
changes any Phase 0 decision on this GTX 1660.

**A1 (VRAM):** essentially unchanged — 5578–5660MB peak vs Vulkan's 5529–5557MB, margin 484–566MB
vs Vulkan's 587–615MB. Same verdict: 8k cap holds, don't force full offload.

**A2 (no-draft throughput): dramatically faster.** Prompt processing jumped from ~39–45 tok/s
(Vulkan) to 93–102 tok/s (CUDA) — roughly **2.3x**. Generation jumped from ~6.1–7.8 tok/s (Vulkan)
to 19.8–22.7 tok/s (CUDA) at 500–4000 tokens — roughly **2.8–3.2x** — *except* at 8000 tokens, where
generation collapsed to 3.5 tok/s (prompt processing also dropped to 75.3 tok/s). That collapse
lines up with A1's margin shrinking toward zero as context fills — likely spilling to CPU right at
the edge of this card's VRAM budget. **This changes the A3 threshold conversation**: CUDA alone,
no draft model, already beats Vulkan's drafted numbers for prompts under ~4k tokens.

**A3 (speculative decode): CUDA cannot run it — reproducible crash, not a config issue.** Loading
the 0.5B draft model alongside the 7B fails on both the CUDA 12.4 and CUDA 13.3 builds with
`llama_model_load: error loading model: invalid vector subscript`, immediately after the same
model loads fine standalone (confirmed by loading the 0.5B alone as a normal model — works).
Tried explicit `--spec-draft-device CUDA0` — same crash. This looks like an upstream llama.cpp bug
in the CUDA backend's draft-model loading path for this GGUF, not present in the Vulkan build.
**Verdict: use Vulkan specifically for the speculative-decode path until this is fixed upstream, or
track/report the bug in llama.cpp.** Given A2's CUDA numbers already beat Vulkan+draft for shorter
prompts, it's worth asking whether CUDA-without-draft is actually the better default and draft
decoding is only needed for the longer end of the range.

**A4 (router latency): faster but still fails the bar.** p50 2693ms / p95 3793ms on CUDA vs p50
3348ms / p95 4550ms on Vulkan (router runs on CPU either way — the improvement is presumably host
contention/driver overhead, not GPU compute). Still ~2.5x over the plan's 1.5s p95 threshold.
**Same verdict as Vulkan: needs the heuristic pre-filter.**

**Recommendation:** benchmark the CUDA no-draft path across more of the length range (especially
4k–8k, where A2 showed a cliff) before deciding between "CUDA, no draft" and "Vulkan + draft" as
the shipped configuration — right now neither backend cleanly wins across the whole range.

## Main model swapped: 7B → 3B (2026-07-06)

Per direction from Richard: main codegen model changed from Qwen2.5-Coder-7B-Instruct to
**Qwen2.5-Coder-3B (base)**, paired with the same 0.5B base draft. No official Qwen GGUF exists for
the base 3B either — used bartowski's `Qwen2.5-Coder-3B-Q4_K_M.gguf` (1.84GB), same quant level as
the 7B for consistency. Both models loaded and generated correctly together on Vulkan on the first
try (`--model-draft` + `--spec-draft-n-max 8`, ctx 8192).

**A1 (VRAM): the tight-margin problem from the 7B is gone.** Peak VRAM at ctx 8192 is 4120MB
(margin 2024MB) vs. the 7B's 5529–5578MB (margin 566–615MB) — roughly **3.4x more headroom**. ctx
10240 barely moves the needle (4135MB). This card was never comfortable running the 7B; it's very
comfortable running the 3B, with enough slack left to consider raising the context cap in a future
Phase 0 pass.

**A2 (no-draft baseline): 6–8x faster than the 7B.** Generation ran 35–62.5 tok/s across the length
sweep (vs. 6.1–7.8 tok/s for the 7B on Vulkan), prompt processing 447–522 tok/s (vs. 38–45 tok/s).
Even the 8000-token case, where both the 7B (Vulkan) and CUDA-7B degraded, held at 35 tok/s here —
no cliff.

**A3 (speculative decode): still a net win, but a smaller relative one, because the baseline is
already fast.** C# task generation ran 63.9–64.6 tok/s with the draft vs. ~45–62.5 tok/s no-draft
at comparable lengths — a real but modest gain (draft matters less when the main model alone is
already this fast). One data point (2000 tok fill prompt) shows a bogus `1000000 tok/s` artifact —
same as the earlier 0.5B-standalone test, caused by the model hitting a stop token almost
instantly so `predicted_ms` rounds to ~0; not a real number, ignore that row.

**Verdict: 3B (base) + 0.5B (base) is a clearly better fit for this GTX 1660 than 7B + 0.5B** —
more VRAM headroom, 6-8x the no-draft throughput.
Trade-off not measured here: code quality/correctness on the actual C# task set — Phase 0 covers
speed and fit, not output quality, so a quality pass (Roslyn parse/compile check against the golden
set once Part B exists) is the natural next step before locking this in.

## Correction: the CUDA draft-loading bug is 7B-specific, not backend-wide (2026-07-07)

The "Model lineup change" section above concluded, from 7B+0.5B testing, that **"the draft pair
only works on Vulkan regardless of which 0.5B variant is used."** That conclusion was wrong — it
generalized from a sample of one main model. Directly asked ("does this pair run in CUDA?") and
tested the 3B (base) + 0.5B (base) pair against the CUDA build: it loaded cleanly on the first try
and ran correctly, no `invalid vector subscript` crash.

Full A2/A3 sweep on CUDA for the 3B pair:

- No-draft (A2): 58.3–64.5 tok/s gen (500–4000 tok), prompt processing 267–332 tok/s.
- With draft (A3): 58.1–65.4 tok/s gen across the length sweep and all 5 C# tasks.
- Comparable to, slightly better than, the Vulkan numbers for the same pair (58.1–64.6 tok/s with
  draft) — CUDA holds up better at 4000 tokens specifically (58.1–58.3 vs. Vulkan's 45–45.6).
- Two rows show the same `1000000 tok/s` artifact seen elsewhere (near-instant stop token) — ignore

**Corrected conclusion:** the CUDA `invalid vector subscript` crash is specific to loading a 0.5B
draft alongside the 7B GGUF used here (`qwen2.5-coder-7b-instruct-q4_k_m.gguf`) — not a general
CUDA-backend limitation on draft-model loading. **The 3B+0.5B draft pair runs fine on both Vulkan
and CUDA.** If the 7B is ever reconsidered as the main model, the CUDA crash would need to be
re-tested and probably reported upstream; it doesn't block the current 3B-based plan.

## New checkpoint: Qwen3-Embedding-0.6B tested as an embedding model (2026-07-07)

Per direction from Richard, tested `Qwen3-Embedding-0.6B-Q8_0.gguf` (official Qwen GGUF, 610MB) —
a different model family from the Qwen2.5-Coder lineup used elsewhere in this doc, and a different
kind of model: it produces vector embeddings, not generated text, so it's not a drop-in replacement
for any existing role — it's a new capability (semantic search/retrieval/caching) rather than a
codegen or router model.

**Setup:** llama-server in embedding mode (`--embedding --pooling last`) rather than `/completion`
mode. Loaded and served correctly on the first try on Vulkan.

**Results:**
- Output: 1024-dimension embedding vectors via the `/embedding` endpoint.
- VRAM: 4015MB at ctx 4096 — notably larger footprint than the 3B main model alone (4120MB at ctx
  8192 is comparable, so this isn't cheap to run alongside the main+draft pair on a 6GB card;
  budget for it separately or expect contention if all three are loaded at once).
- Latency: 285ms on the very first call (cold/warmup), settling to 60–142ms for short code-snippet
  inputs on subsequent calls.
- **Correctness sanity check:** embedded two semantically-similar C# snippets (both a LINQ `Sum`
  over an order/cart total) and one unrelated sentence. Cosine similarity between the two similar
  snippets was **0.78**; between a snippet and the unrelated sentence, **0.19**. Clear separation —
  the embeddings are semantically meaningful, not noise.

**Not yet decided:** what this model is for in the pipeline. Plausible uses: semantic caching
(match new prompts against previously-served ones), context retrieval for TokenSaver, or improving
router accuracy by embedding-similarity against labeled examples instead of (or alongside) the
1.5B classifier. Needs a decision on the actual use case before it goes further than "confirmed it
works."

## Tested Qwen3.5-0.8B + Qwen3.5-4B as a draft pair — loads and runs, but no speculative-decode speedup (2026-07-07)

Per direction from Richard, tested `Qwen3.5-0.8B` (draft) + `Qwen3.5-4B` (main), both unsloth
Q8_0/Q4_K_M GGUFs. **Qwen3.5 is a materially different architecture from everything else in this
doc** — released Feb 2026, it's a hybrid model (Gated DeltaNet linear-attention blocks mixed with
regular attention blocks, `6 × (3 × (Gated DeltaNet → FFN) → 1 × (Gated Attention → FFN))`) with a
vision encoder, not a plain transformer like the Qwen2.5-Coder line. It also has a native
multi-token-prediction (MTP) mechanism, and Qwen's own docs recommend `--speculative-algo NEXTN`
(self-speculative via the model's own MTP head) rather than a separate draft model for vLLM/SGLang.
A separate `-MTP-GGUF` variant exists on unsloth specifically for that path; this test used the
plain (non-MTP) GGUFs with the classic external-draft-model approach used elsewhere in this doc.

**What worked:** both models loaded on llama-server b9878 (Vulkan) with `--model-draft` and no
crash — confirms this build does support the qwen3_5 architecture. VRAM went from 4823MB (4B solo)
to 5637MB (4B+0.8B paired), confirming the draft model actually loaded onto the GPU, not silently
skipped. Generated output was coherent, valid-looking C#.

**What didn't work: no measurable speedup.** Solo 4B baseline held a rock-steady 45.36–45.37 tok/s
across 3 repeated runs of the same prompt. The paired (4B+0.8B draft) run over the same prompt was
41.4–46.8 tok/s across 3 runs — noisier and no better on average than solo. Compare this to the
Qwen2.5-Coder-3B+0.5B pair, which showed a clean, consistent, repeatable gain over its own solo
baseline. This pairing shows none of that signature. (Note: this llama-server build never exposes
`draft_n`/`draft_n_accepted` in the `/completion` response for *any* model tested in this doc — Qwen2.5
or Qwen3.5 — so their absence here isn't itself diagnostic; the side-by-side timing comparison is
what shows the lack of benefit.)

**Interpretation:** the pair is technically functional (loads, runs, no crash) but does not deliver
what makes a draft pair worth using. Most likely explanation: llama.cpp's classic draft/verify
speculative-decoding path assumes a plain causal-attention architecture where a draft model's
proposed tokens can be cheaply verified against the main model's KV cache; Qwen3.5's hybrid
Gated-DeltaNet state doesn't necessarily behave the same way under that algorithm, and/or this
architecture's real acceleration path is the MTP head (untested here) rather than external-model
drafting. **Not recommending this pair as a draft configuration.**

## Followed up: tested Qwen3.5-4B's native MTP self-speculative decoding — also not a win here (2026-07-07)

Downloaded `unsloth/Qwen3.5-4B-MTP-GGUF` (Q4_K_M, includes the MTP head weights) and ran it with
`--spec-type draft-mtp` — the "correct" acceleration path per Qwen's own docs (self-speculation via
the model's own multi-token-prediction head, no separate draft model file).

**Loading:** both Vulkan and CUDA print the same warning on load: `fused Gated Delta Net (chunked)
not supported, set to disabled` — a llama.cpp-level gap (missing kernel), not backend-specific.

**MTP self-speculation is genuinely active** — the server log (not the `/completion` JSON, which
never surfaces draft stats in this build) shows real acceptance-rate lines per request:
`draft acceptance = 0.48–0.70 (many/many accepted), mean len = 2.4–3.1`. So the mechanism works and
is accepting a meaningful fraction of drafted tokens.

**But it's still a net throughput loss.** Repeated the same 3-run same-prompt comparison used for
the earlier draft-pair test:

| Config | Backend | gen tok/s (3 runs) | Avg |
|---|---|---|---|
| Solo 4B, no spec-decode | Vulkan | 45.36, 45.36, 45.37 | 45.36 |
| 4B + 0.8B draft pair | Vulkan | 41.4, 46.8, 45.1 | 44.4 (~flat) |
| 4B MTP, `--spec-type draft-mtp` | Vulkan | 43.1, 24.8, 39.6 | 35.8 (**worse, and noisy**) |
| 4B MTP, `--spec-type draft-mtp` | CUDA | 39.0, 41.2, 37.8 | 39.3 (**worse**) |

Both MTP runs land below the plain solo baseline despite the drafted tokens actually being
accepted at a decent rate — consistent with the "fused Gated Delta Net...disabled" warning: the
fallback path for the un-fused operator appears to cost more than the accepted draft tokens save.

**Conclusion: neither speculative-decoding approach (external draft pair or native MTP) currently
delivers a speedup for Qwen3.5-4B on this llama.cpp build (b9878) on this hardware.** Plain solo
generation (45.36 tok/s) is the fastest configuration found for this model. This is likely a
temporary llama.cpp limitation (missing fused-kernel support for the new architecture, per the load
warning) rather than a fundamental one — worth re-testing against a newer llama.cpp build once
fused Gated Delta Net support lands, but not worth pursuing further right now.

## Qwen2.5(-Coder) vs Qwen3(.5): speed comparison (2026-07-07)

Pulling together every generation-speed number collected so far, split by model family, to answer
directly: which family is actually faster on this GTX 1660 / llama.cpp b9878 combination?

| Model | Family | Backend | Config | Gen tok/s |
|---|---|---|---|---|
| Qwen2.5-Coder-7B-Instruct | 2.5 | Vulkan | solo, no draft | 6.1–7.8 |
| Qwen2.5-Coder-7B-Instruct | 2.5 | CUDA | solo, no draft | 19.8–22.7 (collapses to 3.5 at 8k ctx) |
| Qwen2.5-Coder-7B + 0.5B draft | 2.5 | Vulkan | speculative | 18.3–19.1 |
| Qwen2.5-Coder-0.5B-Instruct | 2.5 | either | solo, standalone fast-path | 156–167 |
| Qwen2.5-Coder-3B (base) | 2.5 | Vulkan | solo, no draft | 35–62.5 |
| Qwen2.5-Coder-3B (base) | 2.5 | CUDA | solo, no draft | 58.3–64.5 |
| Qwen2.5-Coder-3B + 0.5B draft | 2.5 | Vulkan | speculative | 63.9–64.6 |
| Qwen2.5-Coder-3B + 0.5B draft | 2.5 | CUDA | speculative | 58.1–65.4 |
| Qwen3.5-4B | 3.5 | Vulkan | solo, no draft | 45.36–45.37 |
| Qwen3.5-4B + 0.8B draft | 3.5 | Vulkan | speculative (external) | 41.4–46.8, avg 44.4 (~flat, no gain) |
| Qwen3.5-4B MTP | 3.5 | Vulkan | speculative (self, MTP) | 24.8–43.1, avg 35.8 (**worse than solo**) |
| Qwen3.5-4B MTP | 3.5 | CUDA | speculative (self, MTP) | 37.8–41.2, avg 39.3 (**worse than solo**) |
| Qwen3-Embedding-0.6B | 3 | either | embedding, not generation | N/A — not comparable, different task type |

**Headline finding: Qwen2.5-Coder beats Qwen3.5 on this hardware/build, and the gap is entirely
about speculative decoding, not raw solo throughput.**

Solo-generation throughput is actually pretty close once model size is accounted for — Qwen2.5-Coder-3B
(35–64.5 tok/s depending on backend) and Qwen3.5-4B (45.36 tok/s, very consistent) are in the same
ballpark, with Qwen3.5-4B's newer architecture giving it steadier numbers despite being the larger
model. If solo generation were the only thing that mattered, the two families would be roughly a wash.

The gap opens up entirely on speculative decoding, which is the whole point of this pipeline design.
Every Qwen2.5-Coder draft pair tested (7B+0.5B, 3B+0.5B, on both backends) delivered a real speedup
over its own solo baseline. Every Qwen3.5 speculative configuration tested (external 0.8B draft pair,
native MTP self-speculation, on both backends) delivered **zero or negative** speedup over Qwen3.5's
own solo baseline — confirmed not to be a config mistake, since the MTP path's server logs show
genuine draft acceptance rates of 0.48–0.70. The likely cause, per the load-time warning on every
Qwen3.5 run (`fused Gated Delta Net (chunked) not supported, set to disabled`), is that llama.cpp's
support for Qwen3.5's hybrid Gated DeltaNet + attention architecture is still missing key fused
kernels, so the fallback path burns more than the accepted draft tokens save.

**Practical conclusion (speed):** for this project's actual configuration — main model backed by a
speculative draft pair — Qwen2.5-Coder-3B + Qwen2.5-Coder-0.5B (58–65 tok/s with draft, either
backend) is faster in practice than anything achievable with Qwen3.5-4B today (45.36 tok/s solo is
Qwen3.5's ceiling on this build, since both of its speculative paths are net-negative). Qwen3.5 is
architecturally the newer/more efficient design on paper, but llama.cpp b9878's incomplete kernel
support for it negates that advantage here. Worth re-testing once fused Gated Delta Net support
lands upstream; not a reason to switch off Qwen2.5-Coder now.

## First output-quality check: Qwen2.5-Coder-3B(base)+0.5B(base) on the 5 C# tasks (2026-07-07)

Phase 0 up to this point measured speed and VRAM only, never whether the 3B-base main model
actually produces correct code — flagged repeatedly as an open risk since base models aren't
instruction-tuned. Ran the same 5 prompts from `tests/prompts/csharp-tasks.json` against the live
3B(base)+0.5B(base) draft pair (Vulkan, ctx 8192, `n_predict 700`, `temperature 0.2`, greedy-ish),
saved raw output to `tests/quality-check/*.txt`, and compile-checked the extracted code with a
scratch `dotnet build` project (stubbing only types the prompt said to "assume exist").

| Task | Result | Issue |
|---|---|---|
| DTO | **Compiles clean** | Correct records, matches spec exactly. Only ding: wrapped the code in explanatory prose before/after despite "no comments, just the code" — base model doesn't reliably follow negative formatting instructions. |
| Service class | **Fails to compile** | `CS0136`/`CS1656`: declares a `foreach` iteration variable named `discount` that collides with an outer `decimal discount` local, then tries to assign to the iteration variable. A real logic bug, not a style nit — this method would not build as generated. Also invented its own stand-in `Order`/`ITaxRateProvider`/`IDiscountRepository`/etc. rather than treating them as pre-existing per the prompt. |
| Async method | **Compiles only with an unrequested dependency accepted** | Injected an `EF Core DbContext` into the constructor and used `BeginTransactionAsync`/commit/rollback — nothing in the prompt mentioned EF Core; the prompt said stock decrement happens "via the injected `IStockRepository`." A hallucinated dependency that wasn't asked for and doesn't match the stated architecture. Prose also claims it used a `TransactionScope`, which isn't what the code actually does — prose/code mismatch. |
| LINQ-heavy | **Compiles clean, but deviates from spec** | Logic is correct (group, filter ≥2 orders, order by spend desc, take N), but the prompt explicitly asked for `CustomerSpendSummary` as a **record**; the model emitted a mutable `class` instead. Functionally fine, spec-non-compliant. |
| Interface impl | **Generation failure** | Ran into a degenerate repetition loop — `using System.Xml.Linq; using System.Xml.XPath;` repeated dozens of times, consuming the entire `n_predict 700` budget before emitting any actual `EmailNotificationSender` implementation. No usable code produced at all for this task at these settings. |

**Score: 1 of 5 clean, 1 of 5 spec-deviating-but-working, 1 of 5 dependency-hallucinating, 1 of 5
compile-broken, 1 of 5 total generation failure.**

**This is a real finding, not a rounding error.** The 3B-base+0.5B-base pair is 6-8x faster than the
7B and has far more VRAM headroom, but at least two of five realistic tasks produced code a
developer could not merge as-is (one doesn't compile, one silently invents an architectural
dependency that isn't there), and one task failed to generate anything usable in a fixed token
budget. Likely contributors: (a) base models, not instruct-tuned, so they don't reliably track
multi-constraint prompts or negative instructions ("no comments," "assume X exists"); (b) `n_predict
700` may be too tight for the longer interface-impl task specifically — worth re-running that one
task alone with a larger budget before concluding it's a hard failure rather than a truncation
artifact; (c) `temperature 0.2` was chosen to reduce repetition risk and didn't fully prevent it on
this task.

**Practical conclusion (quality): the 3B(base) main model cannot be locked in on speed/VRAM numbers
alone.** Before treating the 7B→3B swap as final, this needs either (1) a real quality pass against
the Part B golden set once it exists, or at minimum (2) a rerun of the interface-impl task with a
larger `n_predict` to rule out truncation, and (3) a comparison against Qwen2.5-Coder-3B-**Instruct**
as main model to see whether instruction-tuning fixes the hallucinated-dependency and
spec-deviation issues without giving up the vocab/logit compatibility that made the base-model
draft pairing work. This is now the single biggest open risk in the current model lineup — bigger
than anything the speed numbers alone would suggest.

## Follow-up: interface-impl retest + Qwen2.5-Coder-3B-Instruct comparison (2026-07-07)

Two follow-ups to close out the open questions above.

**1. Interface-impl retest, same base model, larger budget.** Reran just the interface-impl prompt
against the 3B(base)+0.5B(base) pair with `n_predict` raised 700 → 1800. **It did not repeat the
loop this time** — produced a complete, plausible `EmailNotificationSender` in 1157 chars, well
under even the old 700-token budget. So the earlier failure was **not** a truncation artifact; it
was decoding variance (the same prompt/settings can land in a degenerate repetition loop on one
sample and not another). This is arguably worse news than a truncation bug: it means the failure
mode is non-deterministic and won't be fixed by a bigger token budget alone. The retry itself
introduced a *different* bug — see below.

**2. Qwen2.5-Coder-3B-Instruct vs 3B-base, same 5 tasks, same draft pair.** Downloaded the official
`Qwen/Qwen2.5-Coder-3B-Instruct-GGUF` (Q4_K_M), paired it with the same 0.5B-base draft (loaded and
ran fine — the 0.5B-base is compatible as a draft for both the base and Instruct 3B), and hit it
with the same 5 prompts via `/v1/chat/completions` (proper chat-template formatting this time,
since Instruct models need it). All 5 finished with `finish_reason: stop` — no repetition loops, an
improvement in generation stability over the base model. But compiling the output told a different
story:

| Task | 3B-base result | 3B-Instruct result |
|---|---|---|
| DTO | Compiles clean | Compiles clean |
| Service class | Fails: `discount` variable shadowing (`CS0136`/`CS1656`) | **Fails: references an undefined `OrderLineItem` type** (`CS0246`) — declared `List<OrderLineItem> LineItems` but never defined `OrderLineItem` |
| Async method | Compiles, but hallucinated an unrequested EF Core `DbContext` dependency | **Fails: self-inconsistent hallucinated interface** (`CS0815`) — invented its own `IUnitOfWork.BeginTransactionAsync()` returning plain `Task`, then tried to `var transaction = await ...` and call `transaction.CommitAsync()`/`RollbackAsync()` on it; awaiting a `Task` yields void, so this doesn't compile even on its own terms |
| LINQ-heavy | Compiles clean, deviates from spec (class instead of record) | Compiles clean, same deviation (class instead of record) |
| Interface impl | Generation failure (repetition loop) on first sample; retried sample compiled but **same bug as Instruct below** | **Fails: identical bug** — `string body` declared inside the `try` block, referenced again inside the `catch` block on the retry-once call (`CS0103`, name doesn't exist in that scope) |

**The most interesting finding: the exact same "retry-on-catch references try-scoped variable" bug
appeared independently in the base-model retry AND the Instruct model, both times on the
interface-impl task specifically.** That's not an instruction-following gap — it's a specific,
repeatable blind spot this model family has for the "retry once on transient exception" pattern,
present regardless of instruction-tuning. Worth flagging if this pattern shows up in the actual
pipeline's usage.

**Instruct did not meaningfully outperform base on defect rate: still 2 of 5 clean/compiling
(DTO, LINQ-heavy) vs. base's 2 of 5 (DTO, LINQ-heavy) — same two tasks, same result, different
bugs on the other three.** Instruct's generation was more *stable* (no repetition loops, cleaner
chat-formatted responses, better prose separated from code via proper code fences) and its
hallucinations were more sophisticated (a fully worked-out but internally-inconsistent `IUnitOfWork`
abstraction, vs. base's simpler EF Core name-drop) — but it did not produce more *correct* code on
this task set.

**Revised practical conclusion:** switching 3B-base → 3B-Instruct as the main model would likely
improve generation robustness (fewer degenerate loops, better format adherence) but should **not**
be expected to fix the underlying correctness problem — retry-on-catch scoping bugs and
undefined-type/interface-consistency errors showed up on both. The real fix has to be architectural:
either (a) a Roslyn compile-gate in the pipeline that catches exactly this class of error before
code reaches the user (which is already the stated Phase 4 design goal — this data is a concrete
argument for prioritizing it), or (b) a much stronger main model than either 3B variant, traded off
against the speed/VRAM budget this whole Phase 0 effort was built around. **3B (either variant)
should be treated as "fast but needs a compile gate," not "good enough to trust raw."**
